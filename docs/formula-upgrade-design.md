## 一、当前理解

本次不是把普通 OCR 猜出的字符改名为“公式”，而是新增一条独立的数学公式链路：用户既可对整页自动扫描公式，也可框选单个公式精确识别；识别结果保存为 LaTeX，可在浏览器实时排版、人工校对并标记确认，随后以 Markdown 数学块和 Word 原生可编辑公式导出。普通中文 OCR 仍是默认轻量路径，公式模型缺失或失败时不得破坏现有文档。

## 五、设计方案

### 5.1 推荐方案

1. **双引擎隔离**：保留 RapidOCR 核心环境；PaddleOCR 的 PP-FormulaNet_plus-M 放在独立公式运行时，由受限子进程按 JSON 协议调用。未安装时返回可操作的状态提示，普通 OCR 继续可用。
2. **两种入口**：整页“自动找公式”调用官方 FormulaRecognitionPipeline；框选“识别这个公式”先裁剪原图，再调用 FormulaRecognition，适合纠错和公式密集页面。
3. **统一公式对象**：formula block 保存 `latex`、`display`、`verified`、`formula_source`、`confidence` 与 bbox；`text` 同步保留 LaTeX，兼容已有导出和历史文档。
4. **人机校对**：前端用 KaTeX 的 HTML+MathML 模式实时预览，允许编辑源码、复制、标记已核对；模型输出默认未确认，不以“识别成功”冒充“内容正确”。
5. **可编辑导出**：Markdown 使用 `$...$` / `$$...$$`；DOCX 将 LaTeX 先转 MathML，再映射到 OMML，常见分式、根式、上下标、求和积分、矩阵和分段式保持为 Word 可编辑数学对象。无法转换时保留 LaTeX 并附警告，而不是丢内容。
6. **合并规则**：自动扫描所得公式按 IoU 去重；与普通 OCR 高重叠的乱码文本块移除，人工编辑或已确认的公式不被自动覆盖。

### 5.2 不采用的方案

| 方案 | 核心做法 | 不采用原因 |
|---|---|---|
| 把整个文档默认交给 MinerU/VLM | 一次重做 OCR、布局、表格、公式 | 当前 6 GB 显存和本机轻量定位不适合把重型流水线设为默认；也会替换已验证的核心链路 |
| 仅接 pix2tex 单图模型 | 只做手工裁剪公式转 LaTeX | 缺少整页公式检测，论文和课本使用成本过高 |
| 把 LaTeX 当普通文本写入 Word | 在段落中直接输出源码 | 不满足“可编辑公式”，也无法在 Word 中正常排版 |

### 5.3 复用与新增边界

- 复用：上传、页面图像、归一化坐标、版本冲突、会话隔离、块编辑、导出下载和 worker 状态。
- 扩展：DocumentIR、工作台画框、启动模式、Markdown/DOCX/TXT/PDF/JSON 导出。
- 新增：公式引擎适配器、独立安装脚本、公式 API、KaTeX 预览、MathML→OMML 转换与公式样张验收。
- **明确不做**：不承诺手写/模糊/极端长公式 100% 正确；不上传图片到第三方 API；不在本轮实现整篇论文语义理解、引用解析或 MinerU 全量替换；不把 500 MB 以上模型文件提交进源码包。

## 七、风险与回滚

| 风险 | 触发条件 | 影响 | 缓解措施 |
|---|---|---|---|
| 安装/模型体积大 | 首次安装 Paddle 与约 592 MB 模型 | 下载慢、磁盘增加 | 独立可选环境、状态探测、进度提示；源码包不含模型 |
| CPU 较慢或内存峰值 | 扫描整页、多页连续运行 | 等待时间长 | 默认单页扫描、子进程超时、逐页可取消；保留框选路径 |
| 自动框或 LaTeX 有误 | 复杂版式、低清、手写 | 公式内容错误 | 原图对照、未核对标识、可编辑源码、真实样张基准 |
| OMML 覆盖不全 | 冷门宏包、自定义命令 | Word 降级显示源码 | 常见节点测试；转换失败保留 LaTeX并发出导出警告 |
| 新依赖破坏核心 OCR | Paddle 与 ONNX/Python 包冲突 | 原功能不可用 | 公式环境进程隔离，核心环境只增加小型转换依赖 |

- **回滚方案**：删除安装脚本配置的独立公式运行时即可停用模型；普通文档模式仍可运行。现有 `.data` 文档中新增字段有默认值且历史字段不被删除，SQLite 无迁移回滚。
